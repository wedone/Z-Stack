## 1. CCLoader Sniffer 抓包方法

### 1.1 方案选择

不采用 USB-TTL 直连方案，复用 **CCLoader（ESP8266 + CC2530 烧录器）** 实现无线抓包。

**硬件**：CCLoader 本体的 CC2530 烧 ZBOSS sniffer 固件，ESP8266 GPIO3 (RX) 已接 CC2530 P0_3 (UART0 TX)，零硬件改动。

**软件链路**：

```
CC2530 sniffer ──UART 115200──→ ESP8266 GPIO3 (RX)
                                    │
                                    ▼ 16KB 环形缓冲
                              /api/sniffer/stream
                                    │ HTTP chunked 二进制透传
                                    ▼
                              PC Python 脚本
                                    │ 解析 ZBOSS 协议 (4字节头 + IEEE帧 + CRC状态)
                                    ▼
                              .pcap (DLT_IEEE802_15_4_NOFCS=230)
                                    │
                                    ▼
                              Wireshark / 分析脚本
```

### 1.2 固件准备

#### CC2530 sniffer 固件（基于 ZBOSS v1.0 SDK）

- 源码：`D:\VC\zboss-v1.0\devtools\sniffer\`
- 关键修改：`zb_sniffer_init()` 中 `start_channel = 11; zb_start_sniffer();` 上电自动启动通道 11
- 编译：IAR 打开 `D:\VC\zboss-v1.0\zboss_sniffer.ewp`，选 `Smartrf05Eb-Release` 配置
- 产物：`D:\VC\zboss-v1.0\out\Smartrf05Eb-Release\Exe\zboss_sniffer.hex`
- 烧录：`python tools\burn.py --hex "D:\VC\zboss-v1.0\out\Smartrf05Eb-Release\Exe\zboss_sniffer.hex" --remote zboss_sniffer.bin`

#### CCLoader ESP8266 固件

- 源码：`D:\VC\CCLoader\src\CCLoader.ino`
- 关键：新增 `SNIFFING` 状态 + `/api/sniffer/start|channel|stream|status` 接口
- 修复记录：`enterSnifferMode()` 中**不能**调用 `Serial.write(channel)`（会导致 RX 失效，sniffer 固件已自动启动通道 11）
- 烧录：PlatformIO `python -m platformio run -t upload`

### 1.3 抓包使用

#### 一键抓包（推荐）

```powershell
python tools\sniffer_via_ccloader.py 10.0.0.147 11 cap\test.pcap
```

- 参数：`<ESP8266_IP> <通道号> <输出pcap>`
- 按 Ctrl+C 停止，自动调用 `/api/stop`
- 实时输出包数和缓冲状态

#### 手动控制（调试用）

```powershell
# 启动 sniffer
curl.exe -X POST http://10.0.0.147/api/sniffer/start -H "Content-Type: application/json" -d "{\"channel\":11}"

# 查看状态（bytes_received 应 > 0）
curl.exe http://10.0.0.147/api/sniffer/status

# 停止
curl.exe -X POST http://10.0.0.147/api/stop
```

#### 分析 pcap

```powershell
python tools\analyze_pcap.py cap\test.pcap
```

输出：总包数、时长、速率、帧类型分布、源/目的地址 Top5、5 秒桶时间分布。

#### Wireshark 打开

直接双击 .pcap 文件，DLT=230 自动识别为 IEEE 802.15.4 无 FCS。

### 1.4 注意事项

1. **通道固定 11**：sniffer 固件启动时锁定通道 11，z2m 必须使用通道 11
2. **CC2530 固件互斥**：CCLoader 本体的 CC2530 烧 sniffer 固件后，`/api/burn` 不能再用于烧 HGZBSwitch（会覆盖 sniffer 固件）。建议准备两个 CCLoader：一个专抓包，一个专烧录
3. **8KB vs 16KB 缓冲**：sniffer 模式 16KB（二进制透传），monitor 模式 8KB（Base64）。正常 Zigbee 流量（5 包/秒）下两者都不会丢包，入网/重置瞬时高流量建议用 sniffer 模式
4. **已知 bug**：`/api/sniffer/channel` 接口调用 `Serial.write` 会破坏 RX，暂不可用。切换通道需重新烧录 sniffer 固件
5. **实时性**：HTTP chunked 流式传输，延迟约 50-200ms，足以分析秒级入网流程

### 1.5 备用方案：USB-TTL 直连

如 CCLoader 不可用，可用独立 CC2530+CC2592 模块 + USB-TTL 直连 PC：
- CC2530 P0_3 → USB-TTL RX
- 串口波特率 115200，8N1
- 用 `tools\sniffer_cli.py` 接收（与 CCLoader 方案相同的 ZBOSS 协议解析）
- 缺点：PC 必须靠近 sniffer 模块（USB 线长限制）

## 2. 入网问题分析流程

### 2.1 Zigbee 入网标准流程

设备入网需要完成以下步骤，任何一步失败都会导致入网失败：

```
1. Beacon Request (设备广播)
        ↓
2. Beacon Response (路由器/协调器响应)
        ↓
3. Association Request (设备 → 选定的父设备)
        ↓
4. Association Response (父设备分配 short_addr)
        ↓
5. Data Request (设备等待 Transport Key)
        ↓
6. Transport Key (协调器下发网络密钥)
        ↓
✅ 入网成功
```

### 2.2 分析步骤

#### 步骤 1：统计整体包数

```powershell
python tools\analyze_pcap.py cap\test.pcap
```

关注：总包数、Beacon Request/Response 数量、Association Request/Response 数量、Data Request 数量。

#### 步骤 2：分析入网流程时序

```powershell
python tools\analyze_join.py cap\test.pcap
```

关注：Beacon/Association/Data Request 时序，是否循环重试。

#### 步骤 3：分析 Association 详细字段

```powershell
python tools\analyze_assoc.py cap\test.pcap
```

关注：Association Request 发往哪个设备，Association Response 的 short_addr 和 status。

#### 步骤 4：分析 Beacon Response 来源

```powershell
python tools\analyze_beacon.py cap\test.pcap
```

关注：Beacon Response 来源设备、PAN ID、pan_coord 位、Stack Profile、LQI。

#### 步骤 5：分析信号质量

```powershell
python tools\analyze_signal.py cap\test.pcap
```

关注：各设备 LQI 对比，是否有信号放大芯片导致 RSSI 异常。

### 2.3 常见入网失败模式

#### 模式 A：Association 循环重试

**特征**：
- 4 次 Association Request → 4 次 Association Response → 4 次 Data Request → 失败
- 每次 Association Response 都返回 `status=Success` 和相同 short_addr

**根因**：父设备（路由器）错误响应 Association Request，分配了 short_addr 但**无权发送 Transport Key**（密钥传输需协调器完成）。设备等待 Transport Key 超时后重新发起 Association，循环 4 次后放弃。

**诊断要点**：检查 Association Request 发往的路由器是否为问题设备（如 PTVO 路由器）。

#### 模式 B：收到 Beacon 但不发起 Association

**特征**：
- Beacon Request 收到多个 Beacon Response
- 0 个 Association Request

**可能原因**：
1. 本网 Beacon 全部 `pan_coord=0`（路由器），没有协调器 Beacon
2. 信号强度不足，Beacon RSSI 低
3. 邻居网 Beacon 干扰导致设备混淆
4. 抓包不完整（sniffer 未抓到信号弱的 Association Request）

#### 模式 C：正常入网

**特征**：
- 1 个 Beacon Request → 1 个 Beacon Response → 1 个 Association Request → 1 个 Association Response → 1 个 Data Request → 入网成功
- Beacon Response 来自正确转发的路由器（原厂固件，不响应 Association，转发给协调器）

### 2.4 抓包分析的关键指标

| 指标 | 正常值 | 异常值 |
|------|--------|--------|
| Beacon Request 数 | 1 | 多次重试 |
| Beacon Response 数（本网） | 1-2 | 4-6（多个路由器响应） |
| Beacon Response 数（邻居网） | 0 | ≥2（干扰） |
| Association Request 数 | 1 | 4（循环重试） |
| Association Response status | Success | Success（但无 Transport Key） |
| 设备最终选择的路由器 | 原厂固件路由器 | 问题路由器（PTVO 等） |

### 2.5 LQI 信号质量参考

ZBOSS sniffer 帧末尾最后一字节为 LQI（0-255）：

| LQI 范围 | 信号质量 |
|----------|----------|
| > 200 | 极好 |
| 100-200 | 良好 |
| 50-100 | 较弱 |
| < 50 | 差 |

> 注意：LQI 是 sniffer 接收到的信号质量，不是设备实际接收质量，但可作为相对参考。

## 5. 历史抓包案例参考

### 5.1 案例：PTVO 路由器错误响应 Association

**现象**：3 米无遮挡设备入网失败，5 米两堵墙反而能入网。

**抓包分析**：
- 设备 Beacon Request 收到 6 个 Beacon Response
- 设备按 RSSI 优先选择 0x4B9F（PTVO 路由器，带 RFX2401 信号放大）
- 0x4B9F 响应 Association Request 并分配 short_addr=0xC2B5，status=Success
- 但 0x4B9F 无权发送 Transport Key（密钥传输需协调器完成）
- 设备等待 Transport Key 超时，重新发起 Association，循环 4 次后放弃

**验证**：断电 0x4B9F 后，3 米设备改选 0xBF20（原厂插座）并 1 次成功入网。

**结论**：PTVO 路由器错误响应 Association 是入网失败的直接原因。

### 5.2 案例：邻居网 Beacon 干扰

**现象**：7 米设备断电 0x4B9F 后仍无法入网。

**抓包分析**：
- 设备 Beacon Request 收到 6 个 Beacon（2 本网 + 4 邻居网）
- 本网 Beacon 全部 `pan_coord=0`（路由器），没有协调器 Beacon
- 邻居网有 2 个 `pan_coord=1` 的协调器，但 PAN ID 不同
- 设备未发起任何 Association Request

**可能原因**：设备找不到 PAN coordinator，或邻居网 Beacon 干扰导致设备混淆。

**验证**：后续两次重置都秒级入网成功，均选择 0xBF20（公卫插座），说明问题已随 0x4B9F 断电而解决。

### 5.3 案例：固件 ID 缺失

**现象**：z2m 中借壳设备有固件 ID 显示，但 HGZBSwitch v1.0.10 的固件 ID 缺失。

**分析**：
- v1.0.10 将 SwBuildId 从 `HA-SPA4C1-V1.0.9`（16 字符）改为 `HA-SPA4C1-V1.0.10`（17 字符）
- 超过 16 字符限制，导致 MTU 超限，z2m 读取固件 ID 时丢失

**修正方向**：缩短型号前缀（如 `SPA4C1-V1.0.10`）以保持在 16 字符内。
