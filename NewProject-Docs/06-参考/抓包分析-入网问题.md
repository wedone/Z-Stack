## 3. 问题根因

### 3.1 核心问题 A：ptvo 路由器错误响应 Association Request（3米场景）

**违反 Zigbee 规范的行为**：
- 0x4B9F (ptvo 路由器) 响应了设备的 Association Request
- 分配了 short_addr=0xC2B5 并返回 status=Success
- 但路由器**无权发送 Transport Key**（密钥传输需协调器完成）

**后果**：
- 设备收到 Association Response 后，发送 Data Request 等待 Transport Key
- Transport Key 永远不会到来（0x4B9F 无法发送）
- 设备超时后重新发起 Association，循环 4 次后放弃

**根本原因（PTVO Association 行为异常 + 信号放大双重作用）**：

| 因素 | 说明 |
|------|------|
| **PTVO 路由器错误响应 Association Request** | PTVO 路由器直接响应 Association Request 并分配 short_addr，但**无权发送 Transport Key**。Zigbee 3.0 规定路由器应**转发** Association Request 给协调器，由协调器分配 short_addr 并发送 Transport Key。PTVO 的这一行为违反了 Zigbee 3.0 BDB commissioning 规范。 |
| **PTVO 模块带 RFX2401 信号放大芯片** | 信号强度放大后 RSSI 最高，3米/7米设备按标准 RSSI 优先选择逻辑都选了 0x4B9F，导致必然踩坑 |

两者结合导致：设备总选信号最强的 PTVO 路由器作为父设备，但 PTVO 路由器无法完成 Transport Key 流程，循环失败。

> **关于 PTVO Z-Stack 版本**（详见 3.6 节分析）：此前文档推测"PTVO 基于 Z-Stack 1.2.2a"，但 hex 分析和 Beacon 分析均无法确认此结论。PTVO 的 Beacon 与网络中其他设备（原厂固件）格式一致，问题在于 PTVO 的 Association 行为异常，而非 Z-Stack 版本旧。

**验证**：断电 0x4B9F 后，3米设备改选 0xBF20（原厂插座），1 次 Association 即成功入网，证实 0x4B9F 是直接原因。

### 3.2 核心问题 B：7米设备收到 Beacon 但不发起 Association（7米重置场景）

**现象**：
- 断电 0x4B9F 后，7米设备 Beacon Request 收到 6 个 Beacon（2 本网 + 4 邻居网）
- 本网 Beacon 全部 pan_coord=0（路由器），**没有协调器 Beacon**
- 邻居网有 2 个 pan_coord=1 的协调器，但 PAN ID 不同
- **设备未发起任何 Association Request**

**可能原因**：
1. **设备找不到 PAN coordinator**：Beacon 中无 pan_coord=1 的本网 Beacon
   - 但 3米断电场景同样无 pan_coord=1，设备仍发起 Association 并成功
   - 推测：Z-Stack 3.0.2 不强制要求 pan_coord=1
2. **信号强度不足**：7米设备距 0x7CDA/0x6F89 较远，Beacon RSSI 低
3. **邻居网干扰**：4 个邻居网 Beacon 可能导致设备混淆
4. **抓包不完整**：sniffer 可能未抓到设备的 Association Request（信号弱）

### 3.3 为什么设备选择 0x4B9F 而非协调器？（3米失败场景）

**已确认是 RSSI 优先 + PTVO 信号放大双重作用**：
1. **RSSI 优先**：Z-Stack 3.0.2 的 BDB commissioning 按 Beacon Response 的 RSSI/LQI 排序选择父设备
2. **PTVO 模块带 RFX2401 信号放大芯片**：0x4B9F 与 3米设备并排，加上 RFX2401 放大，RSSI 必然最高
3. **Z-Stack 3.0.2 不强制区分协调器和路由器**：抓包显示所有 Beacon 的 pan_coord=0，设备仍发起 Association

### 3.4 为什么正常入网能成功？

正常入网场景下，设备**只收到 1 个 Beacon Response**（来自 0x3110 书房蚊香插座）：
- 0x3110 是原厂固件路由器，**不响应 Association Request**
- 设备 Association Request 发给 0x3110，但 0x3110 正确转发给协调器
- 协调器分配 short_addr 并发送 Transport Key
- 设备成功入网

### 3.4.1 为什么 7米设备选 0xBF20 而非 0xD334？（信号放大芯片推测）

**抓包证据**（7米重置入网1.pcap 中本网 Beacon 的 LQI 对比）：

| 设备 | 硬件 | 距餐厅开关1 | 遮挡 | LQI |
|---|---|---|---|---|
| 0xBF20（公卫插座） | FB56+SKT14AL2.1 | 较远 | 有遮挡 | **34**（最强） |
| 0x4DA9（客厅开关1，已入网） | HGZBSwitch借壳 | 较近 | 无遮挡 | 23 |
| 0xD334（客厅开关1，HGZBSwitch） | HGZBSwitch借壳 | 较近 | 无遮挡 | 20（最弱） |

**反常现象**：按物理距离，0xD334（客厅开关1）距 7米设备（餐厅开关1）更近且无遮挡，LQI 应该最高；但实际 0xBF20（公卫插座，较远且有遮挡）的 LQI 反而高 70%。

**推测结论**：**FB56+SKT14AL2.1 原厂模块带信号放大芯片**（CC2592 或 RFX2401），HGZBSwitch 借壳固件烧录的模块不带。这与用户描述"PTVO 模块有 2401 信号放大芯片"一致——商业产品普遍带 PA 芯片提升信号。

### 3.4.2 借壳固件路由功能是否正常？（已验证 ✅）

通过 `tools/analyze_routing.py` 分析 7米抓包中 0xD334（HGZBSwitch 借壳固件）的路由行为：

| 抓包 | 总发包 | 广播(Link Status) | 单播 | 作为目的 | Route Req/Reply |
|---|---|---|---|---|---|
| 7米重置入网1 | 25 | 24 | 1 Beacon Response | 0 | 0 |
| 7米重置入网2 | 40 | 37 | 3 (→0x3110) | 0 | 0 |

**结论**：
- ✅ 主动广播 Link Status 维护路由网络拓扑（标准路由器行为）
- ✅ 响应 Beacon Request（7米入网1 中响应了 Beacon）
- ✅ 与 0x3110 有 3 次端到端单播通信
- ✅ 没有 Route Request/Reply（路由器有路由表时不需主动发起，正常）

**借壳固件路由功能完全正常**，问题不在固件，而在硬件信号强度差异（无信号放大芯片）。

### 3.5 次要问题：0x9435 设备卡死

7米抓包中，**0x9435**（厨房烟雾警报器，原厂 M415-6C）反复向 0x7CDA 发送 Data Request（6 次）：
- z2m 中 0x9435 状态正常，但抓包显示它不断请求数据
- 可能是 0x9435 等待某个响应（如路由更新）但 0x7CDA 未回应
- 不影响入网分析，但说明网络中存在大量「等待-重试」流量

### 3.6 PTVO 固件版本分析

**目的**：确定 PTVO 固件基于哪个 Z-Stack 版本，判断是否因版本旧导致不兼容 Zigbee 3.0。

#### 3.6.1 hex 二进制分析

使用 `tools/analyze_ptvo_hex.py` 分析 `ptvo-firmware-2026-06-22/hex/cc2530_rfx2401_p12_p14.hex`（RFX2401 信号放大版本，与 0x4B9F 硬件一致）：

**搜索结果**：

| 搜索目标 | 结果 |
|----------|------|
| `Z-Stack`, `ZStack`, `zstack` | ❌ 未找到 |
| `ZDApp`, `ZGlobals`, `ZDSecMgr` | ❌ 未找到 |
| `bdb_`, `BDB_` | ❌ 未找到 |
| `1.2.2a`, `2.5.1a`, `3.0.1`, `3.0.2` | ❌ 未找到 |
| `ZCL30`, `ZCL25`, `ZCL12` | ❌ 未找到 |
| `ptvo.info` | ✅ 0x0806E |
| `ptvo.switch` | ✅ 0x0807F |
| `2026-06-17` | ✅ 0x080A1（构建日期） |
| `PTVOSIGN1`~`PTVOSIGN8` | ✅ 多处（自定义签名） |
| `ZigBeeAlliance09` | ✅ 0x04427（标准 ZigBee 安装码头，非版本标识） |

**结论**：PTVO hex 中**不含任何标准 Z-Stack 版本字符串**，无法从 hex 直接判断 Z-Stack 版本。PTVO 可能剥离了版本信息，或使用了高度定制的协议栈。

#### 3.6.2 Beacon 分析

分析抓包中 PTVO 路由器（0x4B9F、0x6F89）的 Beacon Response，与其他设备对比：

| 设备 | 类型 | Superframe Spec | Protocol ID | Stack Profile 字节 |
|------|------|-----------------|-------------|-------------------|
| 0x7CDA | 原厂路由器 | 0x8FFF | 0x00 | 0x22 |
| 0xBF20 | 原厂路由器 | 0x8FFF | 0x00 | 0x22 |
| 0x4B9F | **PTVO 路由器** | 0x8FFF | 0x00 | 0x22 |
| 0x3110 | 原厂路由器 | 0x8FFF | 0x00 | 0x22 |
| 0x6F89 | **PTVO 路由器** | 0x8FFF | 0x00 | 0x22 |
| 0xD334 | HGZBSwitch | 0x8FFF | 0x00 | 0x22 |

> **注意**：CCLoader sniffer 的 Beacon 扩展 PAN ID 字段全为 `0xDDDDDDDDDDDDDDDD`（明显异常），说明 sniffer 格式可能与标准 802.15.4 有差异，Beacon payload 字段解析仅供参考。

**结论**：PTVO 的 Beacon 格式与网络中其他设备（原厂固件）**完全一致**，无法从 Beacon 区分 PTVO 使用的 Z-Stack 版本。

#### 3.6.3 综合结论

| 分析方法 | 结论 |
|----------|------|
| hex 字符串搜索 | 无 Z-Stack 版本标识，无法确定 |
| Beacon 格式分析 | 与其他设备一致，无法区分 |
| **行为分析** | **PTVO 路由器错误响应 Association Request 并分配 short_addr** |

**此前文档结论"PTVO 基于 Z-Stack 1.2.2a"无法证实，已修正。** PTVO 的问题在于 Association 行为异常（直接分配 short_addr 而非转发给协调器），这与 Z-Stack 版本无直接关联，可能是 PTVO 固件的实现缺陷或设计选择。

## 4. 验证方案

### 4.1 短期验证：断电 ptvo 路由器（3米场景已完成 ✅）

**目的**：确认 ptvo 路由器是否为入网失败的直接原因。

**操作**：
1. 断电 0x4B9F（客厅开关2）
2. 重置 3米失败的 HGZBSwitch 设备
3. 抓包验证入网流程

**实际结果**：
- 设备 Beacon Request 收到 4 个本网 Beacon（0x6F89, 0x3110, 0xBF20, 0xD334）

- Association Request 正确转发到协调器
- Transport Key 正常下发
- ✅ **入网成功**，short_addr=0x4DA9

**结论**：证实 0x4B9F 错误响应 Association 是 3米失败的直接原因。

### 4.2 待验证：7米设备入网问题

**目的**：解决 7米设备（餐厅开关1）断电 0x4B9F 后仍无法入网的问题。

**待验证假设**：
1. **信号强度不足**：7米设备距本网路由器较远，Beacon RSSI 低
   - 验证：在 7米设备附近临时放置一个原厂路由器，看是否能入网
2. **邻居网干扰**：4 个邻居网 Beacon 干扰设备选择
   - 验证：切换协调器通道（如从 11 换到 15），减少邻居网干扰

   - 验证：断电 0x6F89 后重置 7米设备，看是否能入网

### 4.3 中期验证：HGZBSwitch 固件优化

**方向**：让 HGZBSwitch 优先选择协调器或正确配置的路由器。

**可能措施**：

2. **Beacon 过滤**：只响应 pan_coord=1 的 Beacon（但抓包显示所有 Beacon 的 pan_coord=0）

### 4.4 长期验证：ptvo 路由器行为分析

**可能原因**：

- Zigbee 3.0 应该使用 BDB commissioning，但 ptvo 可能用老式流程
- 协议版本不匹配导致流程混乱

**验证方法**：

- 检查 ptvo 固件的 Z-Stack 配置（是否启用路由器 Association 响应）

## 6. 结论

### 6.1 3米场景（已解决）

**入网失败的直接原因**：ptvo 路由器 0x4B9F 错误响应了 HGZBSwitch 的 Association Request，分配了无效 short_addr 但无法完成 Transport Key 流程，导致设备循环重试后放弃。

**根本原因**：ptvo 固件（基于老版本 Z-Stack）的路由器行为与 Zigbee 3.0 BDB commissioning 不兼容。

**验证方案**：断电 0x4B9F 后，3米设备改选 0xBF20（原厂插座）并成功入网。

### 6.2 7米场景（已解决）

**入网失败的可能原因**（与 3米相同）：ptvo 路由器 0x4B9F 错误响应 Association。

**验证结果**：断电 0x4B9F 后，7米设备两次重置都秒级入网成功，均选择 0xBF20（公卫插座）。

**中间一次失败**（未见 Association）可能是偶然：
- sniffer 距餐厅远，可能未抓到信号弱的 Association Request
- 邻居网 Beacon 干扰导致设备短暂混淆
- 但后续两次都成功，说明问题已随 0x4B9F 断电而解决

### 6.3 3米和 7米场景的共同结论

| 场景 | 断电前 | 断电 0x4B9F 后 |
|---|---|---|
| 3米设备 | ❌ 4次循环失败 | ✅ 1次成功（选 0xBF20） |
| 7米设备 | ❌ 4次循环失败 | ✅ 1次成功（选 0xBF20） |

**ptvo 路由器 0x4B9F 是入网失败的直接原因**，断电后 3米和 7米设备都能秒级入网。

### 6.4 长期方案

**已澄清**：借壳固件（HGZBSwitch）路由功能完全正常（见 3.4.2），入网失败的根因是 PTVO 路由器不兼容 Zigbee 3.0 + 信号放大导致设备优先选错父设备。

**优化方向**（可选）：
1. **BDB commissioning 参数调优**：限制 Association 目标为 PAN coordinator（pan_coord=1）
   - 风险：抓包显示所有 Beacon 的 pan_coord=0（包括协调器本身的 Beacon），强制过滤可能导致无法入网
2. **黑名单机制**：维护一个已知不兼容路由器的短地址/PAN ID 黑名单，避免选错父设备
   - 难点：需要协议栈支持，且 PTVO 设备会变化
3. **增加 Beacon Request 重试次数**：当前只发 1 次，多重试可增加收到协调器 Beacon 的概率
4. **硬件层面**：换用带 CC2592/RFX2401 的模块，提升 RSSI 让自身成为最强信号源
   - 但这会让自家设备也变成"信号放大器"，可能影响邻居网络
