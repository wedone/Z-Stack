# 确定正确的决策

> 记录 v1.0.10 项目历史中已验证为正确的技术决策（与路由问题无关），避免在后续开发中走弯路或被错误"优化"回退。
>
> **原则**：每条决策都有明确的根因分析和验证依据，未经充分评估不得改动。

## 1. 触摸检测用直接低电平读取（不用自适应基线采样）

| 项 | 内容 |
|----|------|
| **决策** | 触摸检测使用直接低电平读取，不使用自适应基线采样 |
| **背景** | WTC6106BSI 触摸芯片输出电平在运行过程中会漂移 |
| **根因** | 自适应基线会被逐步"学习"到触摸电平，导致触摸检测完全失效 |
| **验证** | v0.1.0 移除自适应基线改为直接低电平检测后，触摸功能稳定 |
| **教训** | WTC6106BSI 输出极性固定（未触摸=高，触摸=低），无需自适应 |

```c
// 正确: 直接低电平=触摸
if (!(port & BV(4))) val |= BV(0);

// 错误: 自适应基线（已被废弃）
if ((port & BV(4)) != (touchBaseline & BV(4))) val |= BV(0);
```

## 2. 4 路独立 startUpOnOff 数组（不用单变量）

| 项 | 内容 |
|----|------|
| **决策** | `zclSampleSw_StartUpOnOff` 使用 `uint8[4]` 数组，4 路独立配置 |
| **背景** | Z2M HGZB-4S 定义中 4 路有独立 `power_on_behavior` 配置 |
| **根因** | 单变量会被 Z2M 写入 4 路配置时互相覆盖，最后写入的值覆盖所有 |
| **验证** | v0.2.2 改为数组后，4 路独立断电恢复策略生效 |
| **教训** | 多端点属性必须使用独立变量，不能共用 |

```c
// 正确: 4 路独立数组
uint8 zclSampleSw_StartUpOnOff[SAMPLESW_NUM_RELAYS] = {STARTUP_ONOFF_PREVIOUS, ...};

// 错误: 单变量（已被废弃）
uint8 zclSampleSw_StartUpOnOff = STARTUP_ONOFF_PREVIOUS;
```

## 3. EP11 作为 genBasic 端点（不用 EP8）

| 项 | 内容 |
|----|------|
| **决策** | `SAMPLESW_ENDPOINT` 定义为 11，不用 8 |
| **背景** | EP8 与 `SAMPLESW_ENDPOINT_INPUT4` (=8) 冲突 |
| **根因** | EP8 被注册两次（switch 和 input4），input4 覆盖 switch 的 SimpleDescriptor，z2m interview 找不到 genBasic server cluster → interview 失败 + linkquality 风暴 |
| **验证** | v1.0.3 改为 EP11 后，z2m interview 始终成功 |
| **教训** | 端点号分配必须全局唯一；switch 端点的 genBasic cluster 是 z2m interview 的关键 |

端点布局：
- EP1-4：继电器（genOnOff server）
- EP5-8：输入状态（genAnalogInput server）
- EP11：switch（genBasic / genIdentify / genOnOffSwitchConfig server）

## 4. HAL_KEY=FALSE 根除 P2.0/P0.6 引脚冲突

| 项 | 内容 |
|----|------|
| **决策** | IAR 工程配置 `HAL_KEY=FALSE`，禁用按键模块 |
| **背景** | `hal_key.c` 的 `HalKeyPoll()` 每 100ms 轮询会干扰 P2.0(继电器4)和 P0.6(触摸输入3) |
| **根因** | `hal_key.c` 将 P2.0 定义为摇杆移动输入，触发 `HalAdcRead(HAL_KEY_JOY_CHN, ...)` 读取 P0.6 的 ADC 值，临时修改 `ADCCFG` 寄存器，通过电气干扰影响 GPIO 状态 |
| **验证** | v1.0.0 重构引入 `HAL_KEY=FALSE` 后，LED 状态稳定，无自动熄灭现象 |
| **教训** | 不要用防御性刷新缓解引脚冲突，应直接禁用冲突模块 |

> 注：`hal_key.c` 保留编译但函数为空实现，因 `OnBoard.c` 直接调用 `HalKeyConfig`。

## 5. TX 功率 4dBm（不用 7dBm 或 0dBm）

| 项 | 内容 |
|----|------|
| **决策** | 发射功率设置为 4 dBm（`TX_PWR_PLUS_4`） |
| **背景** | z2m 中 linkquality 极不稳定，从 10+ 到 105 大幅波动 |
| **根因** | 默认 0 dBm 发射功率偏低；7 dBm 在某些模块上 RF 工作不稳定 |
| **验证** | v1.0.5 设置 4 dBm 后，linkquality 数值稳定，不再出现归零现象 |
| **教训** | CC2530 标称最大 7 dBm，但 4 dBm 是更稳妥的选择（与 TI 官方 ZNP 默认一致） |

| 档位 | dBm | 寄存器值 | 测试结果 |
|------|-----|---------|---------|
| TX_PWR_PLUS_7 | 7 | 0xFF | ❌ 信号经常归零，RF 工作不稳定 |
| **TX_PWR_PLUS_4** | **4** | **0xED** | ✅ 与 ZNP 官方默认一致，稳定性最佳 |
| 默认值 | 0 | 0xB6 | ⚠️ 信号偏低，10+ 到 105 波动 |

## 6. 移除 ZCL 命令后主动 Report

| 项 | 内容 |
|----|------|
| **决策** | 移除 `zclSampleSw_HandleOnOffCmd()` 中的 `zclSampleSw_ReportOnOffState(idx)` 调用 |
| **背景** | 连续 z2m 操作 3 轮后设备卡死，约 4 分钟后自动恢复（看门狗复位） |
| **根因** | CC2530 Router 堆大小仅 3072 字节，每次 ZCL OnOff 命令产生 2 条 AF 消息（Report + Default Response），3 轮×4 端点×2 消息 = 24 条 AF 消息，占用约 1200 字节堆，加上协议栈自身使用接近 3072 字节上限，堆耗尽后 OSAL 调度器卡死 |
| **验证** | v1.0.9 移除 Report 后，连续操作 10 轮以上不卡死 |
| **教训** | ZCL 层会自动发送 Default Response，z2m 据此确认命令已接收；主动 Report 是冗余的，浪费堆内存 |

> 注：触摸操作（`ToggleRelay`）仍保留主动上报，因为 z2m 不知道本地触摸事件。

## 7. BDB commissioning 模式选择

| 项 | 内容 |
|----|------|
| **决策** | `zclSampleSw_Init()` 中读取 NV `ZCD_NV_BDBNODEISONANETWORK` 状态选择 commissioning 模式 |
| **背景** | S1 长按复位后无法重新入网，必须断电再上电才能入网 |
| **根因** | 无条件调用 `bdb_StartCommissioning(BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP)`，而该常量值为 `0x00`，不设置任何 commissioning mode 位。BDB 检查 `bdbCommissioningMode == 0` 时直接 report INITIALIZATION 失败并 return，不会调用 `ZDO_InitDevice()` |
| **验证** | v1.0.10 根据 NV 状态选择模式后，S1 复位后可正常入网 |
| **教训** | `BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP` (0x00) 不设置任何 mode 位，新设备必须用 `BDB_COMMISSIONING_MODE_NWK_STEERING` |

修复方案：
- `TRUE`（已配网设备）→ `BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP`（恢复网络）
- `FALSE`（工厂新设备/S1复位后）→ `BDB_COMMISSIONING_MODE_NWK_STEERING`（发现网络并加入）

## 8. LED 不用软件 PWM

| 项 | 内容 |
|----|------|
| **决策** | LED 控制使用直接 GPIO 写入，不用软件 PWM 调光 |
| **背景** | v1.0.6 引入 5ms 周期(200Hz)软件 PWM 调光，导致 RF 信号不稳定 |
| **根因** | PWM 定时器持续运行占用 MCU 资源，干扰协议栈 MAC 时序（CSMA-CA 退避、ACK 等待、rejoin 流程） |
| **验证** | v1.0.8 完全移除 PWM 后，信号稳定性恢复 |
| **教训** | Z-Stack OSAL 应用层定时器周期不建议 < 5ms；LED 调光应使用硬件 PWM 或外部电路 |

## 9. 复位闪烁用自定义状态机（不用 HalLedBlink）

| 项 | 内容 |
|----|------|
| **决策** | S1 长按复位闪烁使用自定义状态机 `zclSampleSw_StartResetBlink()` / `zclSampleSw_ProcessResetBlink()` |
| **背景** | `HalLedBlink(HAL_LED_ALL, 5, 50, 200)` 闪烁频率过快，5 次闪烁看起来只有 3 次 |
| **根因** | `HalLedBlink` 会修改 `HalLedState` 全局变量，与应用层直接 GPIO 操作冲突，导致状态不一致 |
| **验证** | v0.2.4 自定义状态机后，3 次清晰闪烁（6 次状态切换，300ms 亮/300ms 灭，共 1.8 秒） |
| **教训** | 应用层直接操作 GPIO 时，不能使用 `HalLedBlink`，需自定义状态机 |

```c
#define RESET_BLINK_TOTAL_COUNT   6    // 3 次闪烁 = 6 次状态切换
#define RESET_BLINK_PERIOD_MS     300  // 每次亮或灭的持续时间
```

## 10. 触摸轮询 50ms

| 项 | 内容 |
|----|------|
| **决策** | 触摸轮询周期 `TOUCH_POLL_INTERVAL_MS = 50ms` |
| **背景** | v1.0.1 触摸触发延迟 ~200ms，用户感受明显卡顿 |
| **根因** | 100ms 轮询周期导致触发延迟过高 |
| **验证** | v1.0.2 改为 50ms 后，触发延迟降到 ~100ms，接近 WTC6106BSI 硬件响应极限 |
| **教训** | WTC6106BSI 内置 16bit CDC + RISC 处理器，触摸检测本身需要 50-150ms 才能输出有效低电平，50ms 轮询已接近硬件响应极限，更短周期无显著收益 |

| 项 | v1.0.1 | v1.0.2 | 改善 |
|----|--------|--------|------|
| 触摸触发延迟 | ~200ms | ~100ms | ↓ 50% |
| 防抖确认时间 | 200ms (2×100ms) | 100ms (2×50ms) | ↓ 50% |
| S1 长按触发时间 | 5 秒 (50×100ms) | 5 秒 (100×50ms) | 不变 |

> 注：`S1_RESET_THRESHOLD` 从 50 同步调整为 100，保持 5 秒长按复位触发时间不变。

## 11. NV 延迟写入 + 对比写入

| 项 | 内容 |
|----|------|
| **决策** | NV 写入采用延迟写入（Write Coalescing，5 秒合并）+ 对比写入（Compare-Before-Write） |
| **背景** | 继电器状态和 startUpOnOff 配置需写入 Flash 持久化，频繁擦写影响 Flash 寿命 |
| **根因** | CC2530 Flash 擦写次数有限（约 20000 次），无意义擦写会缩短寿命 |
| **验证** | v0.2.0 引入延迟写入 + 对比写入后，Flash 擦写次数大幅减少 |
| **教训** | NV 持久化必须优化写入策略，避免每次状态变化都立即写入 |

## 13. 移除 UI/LCD/MT/Touchlink/GP 模块

| 项 | 内容 |
|----|------|
| **决策** | v1.0.0 重构移除 UI / LCD / MT / Touchlink / Green Power 模块（共 28 个 .c 文件） |

## 14. 借壳 HGZB-4S

| 项 | 内容 |
|----|------|
| **决策** | 借壳型号确定为 HGZB-4S（LXN-4S27LX1.0） |
| **背景** | 自定义 Z2M External Converter 维护成本高 |
| **根因** | HGZB-4S 是 Z2M 内置支持的 4 路开关，默认启用 powerOnBehavior，免 External Converter |
| **验证** | v0.2.0 换壳后，Z2M 自动识别为 HGZB-4S，4 路 onOff 正常控制 |
| **教训** | 优先使用 Z2M 内置支持的借壳型号，减少维护成本 |

> 注：换壳后 Z2M 不再识别 EP5-8 的 input_state 触摸按键状态显示，但触摸操作仍能通过继电器状态变化反映到 Z2M。

## 15. 不用周期性上报

| 项 | 内容 |
|----|------|
| **决策** | 不使用周期性 OnOff 状态上报 |
| **背景** | v0.2.1 引入 30 秒周期性上报恢复状态同步，但无操作时 Z2M 每 30 秒收到 4 个 action 事件 |
| **根因** | z2m 的 `fz.on_off` 转换器在 `state_action: true` 选项启用时，会把每次 OnOff 属性上报转换为 action 事件，即使状态未变化 |
| **验证** | v0.2.3 移除周期性上报后，无操作时 Z2M 不再收到 action 事件 |
| **教训** | 不要为"信号不好"添加防御性机制，应该排查信号根因；状态同步保障改为：入网后立即上报 + 触摸/远程操作后立即上报 + z2m availability 检测 |

## 16. 方案B：重定义 hal_board_cfg 解决 LED 引脚冲突（不用防御性刷新）

| 项 | 内容 |
|----|------|
| **决策** | 通过 PreInclude 机制注入自定义 `hal_board_cfg_linxee.h`，重定义 LED1~4 映射到 P0_0~P0_3，使协议栈 HalLedSet API 直接操作应用层 LED 引脚 |
| **背景** | TI 默认 `hal_board_cfg.h` 为 SmartRF05EB 评估板配置：LED1~3 映射 P1_0/P1_1/P1_4，LED4 (ENABLE_LED4_DISABLE_S1) 映射 P0_1，PUSH2 映射 P2_0。与 linxee 86 开关硬件严重冲突 |
| **根因** | 协议栈 `HalLedSet`/`HalLedBlink` 等 API 操作 TI 默认 LED 引脚 (P1 口)，与应用层直接写 P0_0~P0_3 不一致；ZDApp.c 中 Router 启动逻辑会操作 LED3/LED4，覆盖继电器状态灯；`HAL_BOARD_INIT()` 中 `P0INP |= PUSH2_BV` 会设置 P0_0 三态，影响 LED1 输出 |
| **验证** | linxee v0.2.0 编译通过（0 错误 0 警告），烧录测试 LED 状态稳定，入网后恢复显示继电器状态 |
| **教训** | 开发要着眼大局，用正确的方案从根本上解决问题，而不是一味迁就现状用防御性代码掩盖；谁知道现在将就的方案会不会将来产生 BUG |

### 方案对比

| 方案 | 做法 | 评价 |
|------|------|------|
| ❌ 防御性刷新 | 每 50ms 调用 `UpdateAllRelayOutputs()` 刷新 LED 状态 | 治标不治本，浪费 CPU，掩盖根因 |
| ✅ **方案B (采用)** | 重定义 `hal_board_cfg`，协议栈 LED API 直接操作 P0_0~P0_3 | 从根本上消除冲突，无需防御性代码 |

### 实现细节

**PreInclude 机制**（`preinclude.h`）：
```c
#define HAL_KEY FALSE           // 禁用 HAL_KEY（避免 P0_6 ADC 干扰）
#define HAL_BOARD_CFG_H         // 预定义 include guard，跳过 TI 原文件
#include "hal_board_cfg_linxee.h"  // 注入自定义配置
```

**自定义板级配置**（`hal_board_cfg_linxee.h`）关键修改：
- LED1~4 映射 P0_0~P0_3，极性 ACTIVE_LOW（与应用层反逻辑一致）
- HAL_NUM_LEDS = 4（协议栈可操作 4 路 LED）
- S1 (PUSH1) 映射 P1_3（原 TI 为 P0_1）
- `HAL_BOARD_INIT()` 移除 `P0INP |= PUSH2_BV`（避免影响 P0_0 三态）
- 移除 `ENABLE_LED4_DISABLE_S1` 条件，LED4 独立映射 P0_3

**应用层适配**（`zcl_samplesw.c`）：
- `LedWriteGpio()` 从直接写 `P0_x = val` 改为 `HalLedSet(HAL_LED_1 << idx, ...)`
- 移除 `ProcessTouchPoll()` 中的防御性刷新
- `InitGpio()` 移除冗余 `P0DIR` 设置（已由 `HAL_BOARD_INIT` 的 `LEDx_SET_DIR()` 配置）

### ⚠️ 禁止回退说明

**以下改动不得以"简化"或"优化"为由回退：**

1. **不得移除 `preinclude.h` 的 PreInclude 配置** — 这是方案B的注入入口
2. **不得恢复 `ENABLE_LED4_DISABLE_S1` 宏** — LED4 已独立映射 P0_3
3. **不得恢复 `LedWriteGpio` 的直接 GPIO 写入** — 必须通过 `HalLedSet` API
4. **不得恢复 `ProcessTouchPoll` 中的防御性刷新** — 方案B已从根本上消除冲突
5. **不得恢复 `HAL_BOARD_INIT` 中的 `P0INP |= PUSH2_BV`** — 会影响 P0_0 三态

**如果 LED 出现异常，应排查方向：**
- `hal_board_cfg_linxee.h` 的 LED 引脚映射是否正确
- `HAL_BOARD_INIT()` 是否正确调用 `LEDx_SET_DIR()`
- `HalLedSet` 的 `leds` 参数是否正确映射到 `HAL_LED_1~4`
- **不应**添加防御性刷新作为"修复"
