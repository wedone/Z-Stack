# 已证实的误判

> 记录开发过程中已被证实为错误的修改（已回退），避免重复犯错。
>
> **原则**：每个误判都有明确的引入原因、问题现象、修正方案和教训总结。

## 1. LED 软件PWM调光（v1.0.6~v1.0.8）

| 项 | 内容 |
|----|------|
| **误判** | LED 太亮需要 PWM 调光 |
| **引入版本** | v1.0.6（2026-07-27） |
| **修正版本** | v1.0.8（2026-07-28，完全移除 PWM） |
| **涉及版本** | v1.0.6 ~ v1.0.7 |

### 误判内容

LED 状态灯亮度偏高刺眼，认为需要 PWM 调光降低到 50%。

### 引入方案

引入 5ms 周期(200Hz)软件 PWM，50% 占空比：
- 新增 `SAMPLESW_LED_PWM_EVT` (0x0080) 和 `SAMPLESW_LED_PWM_PERIOD_MS` (5ms) 定义
- 新增 LED 软件 PWM 层（`LedWriteGpio` / `LedSetTarget` / `LedPwmApply`）
- 启动 PWM 定时器持续运行（200Hz）

### 问题现象

- PWM 定时器持续运行干扰协议栈 MAC 时序（CSMA-CA 退避、ACK 等待、rejoin 流程）
- 导致 RF 信号不稳定，z2m 中 linkquality 大幅波动
- 即使入网成功后 PWM 定时器持续运行仍会影响开关的 Zigbee 信号稳定性

### 修正方案

v1.0.8 完全移除 PWM 相关代码：
- 删除 `SAMPLESW_LED_PWM_EVT` 和 `SAMPLESW_LED_PWM_PERIOD_MS` 宏定义
- 删除 `ledTargetOn[]`、`ledPwmCounter`、`ledPwmEnabled` 变量
- 删除 `zclSampleSw_LedPwmApply()`、`zclSampleSw_LedPwmEnable()` 函数
- 删除 `SAMPLESW_LED_PWM_EVT` 事件处理逻辑
- LED 恢复直接写 GPIO 控制（100% 亮度）

### 教训

- **Z-Stack OSAL 应用层定时器周期不建议 < 5ms**，否则会干扰协议栈 MAC 时序
- 200Hz PWM 人眼完全不可见闪烁，是软件 PWM 的安全频率，但即使如此仍会干扰协议栈
- LED 调光应使用硬件 PWM 或外部电路，不应使用软件 PWM
- **不要为"亮度调整"引入会影响协议栈时序的机制**

### 历史细节

- v1.0.6 初始方案用 2ms 周期(500Hz)软件 PWM，导致设备无法入网（z2m 无日志无设备信息）
- 根因：2ms 高频事件流过载 OSAL 队列，干扰 MAC 层时序
- 频率测试：500Hz(2ms) 无法入网 → 200Hz(5ms) 秒入网，确认 5ms 为安全频率上限
- v1.0.7 试图通过"未入网时禁用 PWM"缓解，但入网后 PWM 仍干扰 RF 信号
- v1.0.8 完全移除 PWM 是正确方案

## 2. 30秒周期性上报（v0.2.1~v0.2.3）

| 项 | 内容 |
|----|------|
| **误判** | 信号不好导致 Z2M 状态永久失同步，需要周期性上报恢复 |
| **引入版本** | v0.2.1（2026-07-25） |
| **修正版本** | v0.2.3（2026-07-25，移除周期性上报） |
| **涉及版本** | v0.2.1 ~ v0.2.2 |

### 误判内容

ZCL Report 是无 APS ACK 的单向消息，信号不好时 Report 丢失，设备无感知不重传。即使信号恢复，也没有事件触发重新上报当前状态。Z2M 端无定时 poll 机制，状态永久错位。认为需要 30 秒周期性上报机制恢复同步。

### 引入方案

- 新增事件 `SAMPLESW_STATE_REPORT_EVT` (0x2000)
- 新增宏 `STATE_REPORT_INTERVAL_MS = 30000`（30 秒周期）
- 在 `zclSampleSw_event_loop` 中处理该事件：上报所有 4 路 OnOff 状态后重新启动定时器
- 入网时启动周期定时器

### 问题现象

- 无操作时 Z2M 每 30 秒收到 4 个 action 事件（`on_l1` / `on_l2` / `on_l3` / `on_l4`）
- `state_l1~l4` 保持 `ON` 不变（状态实际未变化）
- MQTT topic `z2m/0x00124b000337c11c/action` 周期性发布，干扰基于 action 的 HA 自动化

### 根因

z2m 的 `fz.on_off` 转换器在 `state_action: true` 选项启用时，会把每次 OnOff 属性上报（即使是相同值）转换为 action 事件。固件每 30 秒上报 `onOff=true`，z2m 每次都生成 `action: on_l1~l4`，即使 state 实际未变化。

### 修正方案

v0.2.3 移除 30 秒周期性上报机制：
- 移除 `SAMPLESW_STATE_REPORT_EVT` (0x2000) 事件定义
- 移除 `STATE_REPORT_INTERVAL_MS` (30000ms) 宏定义
- 移除 `ZDO_STATE_CHANGE` 入网成功后启动周期定时器的代码
- 移除 `zclSampleSw_event_loop` 中 `SAMPLESW_STATE_REPORT_EVT` 事件处理

保留的状态同步机制：
- 入网后立即上报（BUG-007 修复）
- 触摸/远程操作后立即上报（BUG-002 修复）
- z2m availability 检测

### 教训

- **不要为"信号不好"添加防御性机制**，应该排查信号根因
- 信号持续不好时设备亦无法响应 Z2M 命令，周期性上报也无法解决
- 若 Report 丢失，下次操作时会重新上报恢复同步
- z2m 转换器的 `state_action` 选项会把所有上报转为 action 事件，固件不应在状态未变化时主动上报

## 3. LED 防御性刷新（v0.2.4）

| 项 | 内容 |
|----|------|
| **误判** | 协议栈残留代码可能意外修改 P0_0~P0_3，需要定期刷新 |
| **引入版本** | v0.2.4（2026-07-25） |
| **初次修正** | v1.0.0（2026-07-26，通过 `HAL_KEY=FALSE` 根除引脚冲突） |
| **最终修正** | linxee v0.1.1（2026-07-31，方案B重定义 `hal_board_cfg` 从根本上消除冲突） |
| **涉及版本** | v0.2.4（仅一个版本） |

### 误判内容

Z-Stack 协议栈残留代码（尤其 `hal_key.c` 的 `HalKeyPoll()` 每 100ms 轮询）会间接干扰 GPIO 状态，导致 LED1 自动熄灭。认为需要每 50ms 调用 `UpdateAllRelayOutputs()` 定期刷新 LED 状态。

### 引入方案

在 `zclSampleSw_ProcessTouchPoll()` 末尾添加每 50ms 调用 `zclSampleSw_UpdateAllRelayOutputs()` 刷新所有 LED 状态：

```c
// ❌ 已移除: 防御性刷新LED状态 (每50ms)
// Z-Stack协议栈残留代码可能意外修改P0_0~P0_3, 定期刷新确保LED正确显示继电器状态
zclSampleSw_UpdateAllRelayOutputs();
```

### 问题现象

- v1.0.0 已通过 `HAL_KEY=FALSE` 根除引脚冲突，hal_key.c 函数编译为空实现，不再干扰 GPIO
- 防御性刷新是多余的，浪费 CPU 周期
- 基于"可能"的假设添加防御性代码，没有从根本上解决问题
- linxee 分支开发时，防御性刷新曾一度被恢复（因 LED 引脚冲突未从根本上解决）

### 修正方案

**v1.0.0 初次修正**：
- 引入 `HAL_KEY=FALSE` 禁用按键模块，根除 P2.0(继电器4)/P0.6(触摸输入3) 引脚冲突
- hal_key.c 函数编译为空实现，不再干扰 GPIO
- 移除防御性刷新代码

**linxee v0.1.1 最终修正（方案B）**：
- 通过 PreInclude 机制注入自定义 `hal_board_cfg_linxee.h`，重定义 LED1~4 映射到 P0_0~P0_3
- 使协议栈 `HalLedSet`/`HalLedBlink` 等 API 直接操作应用层 LED 引脚
- 从根本上消除协议栈与应用层 LED 引脚冲突，防御性刷新彻底不再需要
- 详见 [确定正确的决策 §16](确定正确的决策.md#16-方案b重定义-hal_board_cfg-解决-led-引脚冲突不用防御性刷新)

### 教训

- **不要基于"可能"的假设添加防御性代码**
- 防御性代码掩盖了根本问题，应直接修复根因
- v0.2.4 的防御性刷新只是缓解症状，v1.0.0 的 `HAL_KEY=FALSE` 解决了 hal_key.c 干扰
- **linxee v0.2.0 的方案B才是真正的最终解决方案**，重定义 hal_board_cfg 使协议栈 LED API 与应用层引脚一致
- **开发要着眼大局，用正确的方案从根本上解决问题，而不是一味迁就现状用防御性代码掩盖**

## 4. 开发测试被问题路由影响

| 项 | 内容 |
|----|------|
| **误判** | 入网问题、z2m 操作卡、信号质量不好等问题归因于固件代码 |
| **发现时间** | 2026-07-30（抓包分析后确认） |
| **影响版本** | v1.0.0 ~ v1.0.10（部分修复可能是不必要的） |

### 误判内容

开发过程中遇到的各种问题（入网失败、z2m 操作卡顿、信号质量不好等）都归因于固件代码，认为需要通过修改固件代码解决。

### 实际情况

通过抓包分析发现，部分问题由测试环境中的问题路由器导致：
- PTVO 路由器（0x4B9F）错误响应 Association Request，分配了无效 short_addr 但无法完成 Transport Key 流程
- PTVO 模块带 RFX2401 信号放大芯片，信号强度最高，设备按 RSSI 优先选择逻辑都选了 0x4B9F
- 断电 0x4B9F 后，3米和 7米设备都能秒级入网

### 问题表现

| 问题 | 误判归因 | 实际原因 |
|------|----------|----------|
| 3米设备入网失败 | 固件 BDB commissioning 问题 | PTVO 路由器 0x4B9F 错误响应 Association |
| 7米设备入网失败 | 固件信号强度不足 | PTVO 路由器 0x4B9F 错误响应 Association |
| z2m 操作卡顿 | 固件响应慢 | 网络环境中有问题路由器 |
| linkquality 波动 | 固件发射功率问题 | 网络环境干扰 + PTVO 信号放大 |

### 教训

- **排查问题时先排除网络环境因素**（路由器、信号干扰），再修改代码
- 没有抓包设备的情况下，盲目改协议栈参数很可能越改越糟
- 同硬件对比商业产品（如 PTVO）是有效的诊断方法
- 建立科学测试方法：抓包分析 + 量化测试基线 + 对比测试
- **停止猜测性修复**：所有"修复"都应基于抓包证据，而非基于现象猜测原因

### 历史修复可信度评估

| 类型 | 例子 | 可信度 |
|------|------|--------|
| 有明确复现+根因+验证 | v1.0.3 端点冲突、v1.0.6 PWM 500Hz 干扰入网 | 高，确实修对了 |
| 单次观察+理论推测+无复测 | v1.0.9 移除 Report、v1.0.7 PWM 入网保护 | 低，可能只是巧合不复发 |
