# 诊断与优化方案 - CC2530 z2m 交互不流畅

> 本文档记录当前项目的诊断方法论和优化计划。目的：让接手的 AI 或开发者能完整理解问题背景、已确认的事实、诊断方法和下一步行动，避免重复劳动或盲目猜测性修复。

---

## 1. 问题陈述

### 1.1 现象
自研 CC2530 4路智能开关固件（HGZBSwitch），接入 z2m（协调器为 CC2652P）后，交互体验**不如同硬件（CC2530）的商业产品流畅**。具体表现：
- z2m 下发命令到设备状态更新，延迟感受上比商业产品慢
- 连续操作若干轮后偶发设备无响应（v1.0.9 已做理论修复，未严格验证）
- S1 长按复位后无法重新入网（v1.0.10 已定位根因并修复）
- 入网成功率不稳定：3米无遮挡反而难入网，5米两堵墙有时反而能入网

### 1.2 已确认的事实（不再怀疑）
| 事实 | 依据 |
|------|------|
| **协调器硬件没问题** | 用户使用 CC2652P，z2m 官方推荐芯片 |
| **不是硬件性能瓶颈** | 对比对象也是 CC2530 商业产品（老设备），硬件同等 |
| **是软件问题** | 同硬件对比商业产品，商业产品流畅，说明软件有差距 |
| **商业产品参考价值高** | 用户的 86 开关本身就是商业产品（厂家倒闭），先刷了 ptvo，无法退回原厂固件做 A/B 对比 |
| **CC2530 在 z2m 生态中是 legacy 芯片** | z2m 官方已转向 CC2652/CC1352 系列，但作为 Router 仍可使用 |

### 1.3 历史修复的可信度评估
v1.0.0~v1.0.9 共 10 个版本，修复可信度分两类：

| 类型 | 例子 | 可信度 |
|------|------|--------|
| 有明确复现+根因+验证 | v1.0.3 端点冲突、v1.0.6 PWM 500Hz 干扰入网 | 高，确实修对了 |
| 单次观察+理论推测+无复测 | v1.0.9 移除 Report、v1.0.7 PWM 入网保护 | 低，可能只是巧合不复发 |

**核心问题**：没有抓包设备，所有"修复"都是基于现象猜测原因，改了代码看现象是否消失。无法真正定位是程序问题还是信号问题，也无法验证修复是否真的有效。

## 2. v1.0.10 入网问题修复（已完成）

### 2.1 根因
`zclSampleSw_Init()` 中无条件调用：
```c
bdb_StartCommissioning(BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP);
```

而 `BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP = 0x00`（见 [bdb.h:175](file:///d:/VC/Z-Stack/Components/stack/bdb/bdb.h#L175)），不设置任何 commissioning mode 位。

**BDB 对新设备的处理流程**（[bdb.c:817](file:///d:/VC/Z-Stack/Components/stack/bdb/bdb.c#L817)）：
1. S1 复位 → `bdb_resetLocalAction()` → `bdb_setFN()` 清除 `bdbNodeIsOnANetwork` 和 NV 网络状态
2. 软复位后 `zclSampleSw_Init()` 传入 mode=0x00
3. BDB 读取 NV，`bdbNodeIsOnANetwork == FALSE`
4. BDB 检查 `bdbCommissioningMode == 0`（确实为0）
5. BDB 直接 report INITIALIZATION 失败并 return
6. **不会调用 `ZDO_InitDevice()`，不会触发 NWK_STEERING**
7. 设备无法发现网络，无法入网

原代码注释"新设备: 触发BDB initialization后启动NWK_STEERING commissioning"是**错误的**。

### 2.2 修复方案
读取 NV `ZCD_NV_BDBNODEISONANETWORK` 状态，根据状态选择 commissioning 模式：
- `TRUE`（已配网设备）→ `BDB_COMMISSIONING_REJOIN_EXISTING_NETWORK_ON_STARTUP`（恢复网络）
- `FALSE`（工厂新设备/S1复位后）→ `BDB_COMMISSIONING_MODE_NWK_STEERING`（发现网络并加入）

### 2.3 为什么断电再上电能入网
冷启动后 ZDApp 的启动逻辑可能走不同分支，或 BDB 层检测到 rejoin 失败后 fallback 到 NwkSteering。软复位后状态不干净，BDB 直接 report 失败而不 fallback。修复后软复位也会显式走 NWK_STEERING，问题解决。

## 3. 整体诊断方法论

### 3.1 核心原则
**停止猜测性修复，建立科学测试方法**。没有抓包设备的情况下，盲目改协议栈参数很可能越改越糟。

### 3.2 量化测试基线
每个版本都必须跑以下测试，用手机慢动作录像或 z2m 日志时间戳量化延迟：

| 测试项 | 方法 | 目标 |
|--------|------|------|
| z2m 下发 ON → 状态更新完成 | 测3次取平均，记录毫秒 | 商业产品通常 <500ms |
| 本地触摸 → z2m 状态更新完成 | 测3次取平均，记录毫秒 | 商业产品通常 <800ms |
| 连续 20 次 ON/OFF 切换 | 记录失败次数 | 0 次失败 |
| S1 复位后入网 | 测5次，记录成功次数 | 5/5 成功 |
| 24小时稳定性 | 记录掉线次数 | 0 次掉线 |

### 3.3 对比测试：ptvo firmware
[ptvo firmware](https://ptvo.info/zigbee-switch-configurable-firmware-v2-210/) 是 CC2530 上的成熟社区固件（基于 Z-Stack 1.2.2a），z2m 兼容性好。烧录到同一块板子，用同样的测试基线对比。

**判断逻辑**：
- ptvo 明显比我们的流畅 → 软件问题，反向工程 ptvo 做了什么
- ptvo 也一样不流畅 → CC2530 硬件瓶颈，软件再怎么调也没用
- ptvo 介于中间 → 部分是硬件，部分是软件，需抓包定位

### 3.4 抓包分析：CC2530+CC2592 sniffer
用额外的 CC2530+CC2592 模块刷 sniffer 固件，配合 TI Packet Sniffer 或 Wireshark + ZBOSS 抓包。这是定位 Zigbee 问题的唯一可靠方法。

**抓包要分析的内容**：
1. **入网流程**：设备发了几次 beacon request？协调器回复了几次 beacon？设备发送 association request 是否成功？
2. **z2m 下发命令**：命令到达设备用了多久？设备回复 Default Response 用了多久？是否有重传？
3. **本地触摸上报**：设备发送 Report Attributes 是否成功？z2m 是否收到？
4. **信号质量**：RSSI 和 LQI 数值，是否有干扰
5. **重传情况**：MAC 层重传次数，APS 层重传次数
6. **协议栈参数**：ptvo 用的 channel、PAN ID、发射功率、rejoin 间隔等

## 4. 执行计划

### 阶段1：修复入网问题（已完成）
- v1.0.10 修复 S1 软复位后无法入网
- 编译、烧录、测试 S1 复位入网 5 次

### 阶段2：搭建抓包环境
- 刷 CC2530+CC2592 sniffer 固件
- 安装 TI Packet Sniffer 或 Wireshark + ZBOSS
- 验证能抓到 z2m 协调器（CC2652P）的 beacon/probe 信号
- 详见独立的《抓包教程.md》

### 阶段3：ptvo 对比测试 + 抓包分析
1. 烧 ptvo 固件到待测开关（先不烧我们的 v1.0.10）
2. 用 sniffer 抓 ptvo 的：入网流程、z2m 下发命令的响应、本地触摸上报
3. 记录 ptvo 的 ZCL 命令序列作为"黄金参考"
4. 烧回 v1.0.10，同样抓包，对比差异
5. 根据差异针对性优化

### 阶段4：针对性优化（根据抓包结果）
可能的方向（需抓包验证后再决定）：
- 触摸改中断（响应 100ms → 20ms）
- 评估 v1.0.9 是否该回退（恢复 Report，改禁用 Default Response）
- 调优 Z-Stack 协议栈参数（APSC_MAX_FRAME_RETRIES、NWK_MAX_DATA_RETRIES 等）
- 调整 BDB commissioning 参数（scan duration、channel mask 等）

### 阶段5（可选）：硬件升级
如果 CC2530 持续不稳定，考虑换 CC2652P 模块（~30-60元），z2m 官方推荐，20dBm 发射功率，更稳定协议栈。
